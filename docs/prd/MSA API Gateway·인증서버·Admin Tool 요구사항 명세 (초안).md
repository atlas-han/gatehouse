# Gatehouse 요구사항 명세 (초안)

Oct 16, 2026 · @Namil Han

## 1. 개요

서비스별로 흩어진 인증을 중앙 인증서버와 API Gateway로 일원화하고, 클라이언트와 정책은 Admin Tool에서 관리한다. 팀의 마이크로서비스 아키텍처 전환에 맞춰 진행하며, 프로젝트 이름은 Gatehouse다.

**배경**: 현재 서비스 간 인증은 IP allowlist 위주이며, 일부는 서비스마다 제각각 구현되어 있다. IP만으로는 어느 서비스가 호출했는지 식별할 수 없다.

**목표**

1. 인증 일원화: 서비스별 개별 인증을 인증서버와 Gateway로 통합한다.
2. 호출자 식별: 모든 내부 호출에서 호출자를 식별하고 기록한다.
3. 정책 관리: 라우트, 클라이언트, IP 정책을 코드 배포 없이 Admin Tool에서 변경한다.
4. 감사 가능성: 인증 실패와 모든 설정 변경을 추적한다.

**범위 (In)**

- S2S 호출자: 내부 마이크로서비스, 사내 타 팀 시스템
- Gateway 담당 트래픽: 내부 서비스 간(East-West) 호출까지 포함, 모든 내부 호출이 Gateway를 경유
- 구성 요소: API Gateway, 인증서버, Admin Tool

**범위 밖 (Out)**

- 외부 파트너·가맹점 대상 API 공개
- 최종 고객(사용자) 인증
- 서비스 내부의 비즈니스 인가 로직
- Service mesh·mTLS (후속 검토)

**환경과 제약**

- 외부 진입 트래픽: 없음
- 사내 타 팀 시스템: 같은 VPC의 다른 EKS 클러스터
- 피크 처리량: 20,000 TPS
- 일정과 인원: 2개월, 1인

**용어**

| 용어 | 의미 |
| --- | --- |
| 클라이언트 | Gateway를 호출하는 등록된 시스템. Client ID로 구분한다 |
| 인증 방식 | 클라이언트 등록 시 고르는 검증 방식. `CLIENT_ID_ONLY`, `CLIENT_SECRET`, `JWT`, `LEGACY_API_KEY` |
| 호출자 식별 | 인증 없이 호출자가 누구인지 기록하는 것. `CLIENT_ID_ONLY`의 목적 |
| 내부 진입 경로 | 내부망에서만 도달 가능한 Gateway 진입점(internal ingress) |
| 레거시 어댑터 | 기존 API Key 등 레거시 인증을 검증해 등록 클라이언트로 매핑하는 Gateway 구성 요소 |

## 2. 시스템 구성

요청 경로는 호출자 → API Gateway → 다운스트림 서비스이고, 관리 경로는 Admin Tool → 관리 API 서비스 → MySQL이다. 설정 변경은 Kafka 이벤트로 Gateway에 전파되고, Gateway는 요청 처리 중 DB를 직접 조회하지 않는다.

&#91;embedded content: 구성 요소 · 요청 경로(왼쪽)와 관리 경로(오른쪽)\]

왼쪽은 매 요청이 지나는 경로이고, 오른쪽은 운영자가 정책을 바꾸는 경로다. Gateway는 인증서버의 JWKS를 캐시해 토큰을 직접 검증하므로, 인증서버가 멈춰도 만료 전 토큰은 계속 통과한다.

| 구성 요소 | 서비스 이름 | 기술 후보 | 역할 |
| --- | --- | --- | --- |
| API Gateway | `gatehouse-gateway` | Spring Cloud Gateway (WebFlux) | 클라이언트 식별, IP 검증, 인증 방식별 검증, 레거시 어댑터, 라우트 인가, rate limit, 라우팅, 클라이언트별 API 지표 |
| 인증서버 | `gatehouse-auth` | Spring Security, Spring Authorization Server | JWT 발급, JWKS 공개, 토큰 폐기, Google OIDC 중계, Admin 역할 부여 |
| 관리 API 서비스 | `gatehouse-admin-api` | 별도 서비스 | 클라이언트·Secret·라우트·역할 관리, 민감 변경 승인, 감사 로그, 변경 이벤트 발행 |
| Admin Tool | `gatehouse-console` | Svelte + Admin BFF (Spring) | 관리 화면, 세션 쿠키 기반 로그인, 관리 API 호출 |
| MySQL | 공용 인프라 | MySQL | 클라이언트, 라우트, 역할, 감사 로그의 원장(source of truth) |
| Kafka | 공용 인프라 | Kafka | 설정 변경 이벤트를 Gateway 인스턴스에 전파 |
| Redis | 공용 인프라 | Redis | 클라이언트별 rate limit, 토큰 폐기 목록 |

## 3. 클라이언트 인증 모델

클라이언트는 등록 시 인증 방식 1개(필수)와 허용 IP(선택)를 서로 독립적으로 설정한다. 미등록이거나 비활성인 Client ID는 인증 방식과 관계없이 거부한다.

| 인증 방식 | 요청에 담는 값 | Gateway 검증 | 성격 | 허용 경로 |
| --- | --- | --- | --- | --- |
| `CLIENT_ID_ONLY` | X-Client-ID 헤더 | 등록·활성 여부 | 호출자 식별 (인증 아님) | 내부 진입 경로만 |
| `CLIENT_SECRET` | X-Client-ID + X-Client-Secret 헤더, 매 요청 | HMAC 다이제스트 상수 시간 비교 | 인증 | 제한 없음 |
| `JWT` | Bearer 토큰 (`client_credentials`로 사전 발급) | 서명, 만료, 대상(audience), 폐기 여부 | 인증 | 제한 없음 |
| `LEGACY_API_KEY` | 기존 레거시 키 | 레거시 어댑터가 검증 후 등록 클라이언트로 매핑 | 기존 방식 수준 | 마이그레이션 기간 한정 |

**IP 검증 규칙**

- 클라이언트에 IP(CIDR)가 등록되어 있으면 검증하고, 비어 있으면 검증하지 않는다.
- IP 검증은 인증 방식과 독립적으로, 인증 방식 검증보다 먼저 수행한다.
- 실제 클라이언트 IP는 신뢰 프록시 체인 기준으로 판단한다. 신뢰 목록 밖의 프록시가 붙인 `X-Forwarded-For` 값은 무시한다.
- 타 팀 시스템은 같은 VPC의 다른 EKS 클러스터에 있어 출발 IP가 Pod IP로 바뀔 수 있다. IP는 단일 주소보다 서브넷 CIDR 단위 등록을 기본으로 한다.

**헤더 규칙**

- `X-Client-ID`와 `Client-ID`, `X-Client-Secret`과 `Client-Secret`은 각각 같은 항목으로 취급한다.
- 두 형식이 함께 오면서 값이 다르면 요청을 거부한다.
- 신원 헤더 정규화 단계에서는 두 형식을 모두 제거한다.

**Gateway 처리 순서**

1. 라우트 매칭
2. 클라이언트 식별: 헤더, 토큰, 레거시 키에서 Client ID를 추출하고 캐시에서 클라이언트 설정을 조회
3. IP 검증: 등록된 IP가 있을 때만
4. 인증 방식 검증: 클라이언트의 인증 방식에 따라 분기, 레거시는 어댑터에 위임
5. 라우트 인가: 이 클라이언트가 이 경로를 호출할 수 있는지
6. Rate limit: 클라이언트별
7. 신원 헤더 정규화: 외부에서 들어온 신원 헤더를 제거하고 검증된 `X-Client-Id`, `X-Auth-Method`를 다운스트림에 주입

다운스트림 서비스는 `X-Auth-Method`가 `CLIENT_ID_ONLY`인 호출의 신원을 인가 판단에 사용하지 않는다.

## 4. 기능 요구사항: API Gateway

Gateway는 모든 S2S 요청에 대해 식별, IP 검증, 인증, 인가를 수행하고 검증된 신원만 다운스트림에 전달한다.

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| GW-01 | 라우트 정의(경로, 메서드, 대상 서비스)에 따라 요청을 라우팅한다. 모든 내부 서비스 간 호출이 대상이다 | Must |
| GW-02 | 요청의 헤더, 토큰, 레거시 키에서 클라이언트를 식별한다 | Must |
| GW-03 | 미등록·비활성 Client ID 요청은 인증 방식과 관계없이 거부한다 | Must |
| GW-04 | 클라이언트에 IP가 등록된 경우에만 IP를 검증한다 | Must |
| GW-05 | 클라이언트의 인증 방식(`CLIENT_SECRET`, `JWT`)에 따라 자격 증명을 검증한다 | Must |
| GW-06 | `CLIENT_ID_ONLY` 클라이언트는 내부 진입 경로로 들어온 요청만 허용한다 | Must |
| GW-07 | 레거시 인증 어댑터: 기존 방식별 플러그인으로 검증하고 결과를 등록 클라이언트로 매핑한다 | Must |
| GW-08 | 라우트별 허용 클라이언트와 최소 인증 수준으로 인가한다 | Must |
| GW-09 | 클라이언트별 rate limit을 적용한다 | Should |
| GW-10 | 외부에서 들어온 신원 헤더(접두사 유무 두 형식 모두)를 제거하고 검증된 `X-Client-Id`, `X-Auth-Method`를 주입한다 | Must |
| GW-11 | 클라이언트·라우트 설정을 메모리 캐시에서 조회하고, 변경은 Kafka 이벤트로 재배포 없이 반영한다. 요청 경로에서 DB를 조회하지 않는다 | Must |
| GW-12 | 접근 로그와 메트릭을 호출자, 인증 방식, 라우트 기준으로 기록한다 | Must |
| GW-13 | 레거시 클라이언트별 호출량을 집계해 전환 현황을 제공한다 | Should |
| GW-14 | 클라이언트별로 호출한 API(라우트 템플릿), 요청 수, 성공·실패율을 집계한다. 실패는 인증 거부, 4xx, 5xx로 구분한다 | Must |
| GW-15 | JWT 검증 시 Redis 폐기 목록을 확인해 폐기된 토큰을 거부한다 | Must |
| GW-16 | 인증서버 장애 중에도 캐시된 JWKS로 만료 전 토큰을 계속 검증한다 | Must |
| GW-17 | `X-Client-ID`와 `Client-ID`, `X-Client-Secret`과 `Client-Secret`을 같은 항목으로 인식하고, 두 형식이 서로 다른 값으로 함께 오면 거부한다 | Must |
| GW-18 | Redis 장애 시 폐기 목록 확인을 일시 중단하고 rate limit을 적용하지 않는다. 장애 진입·복구를 알림으로 남긴다 | Must |

## 5. 기능 요구사항: 인증서버

인증서버는 S2S 토큰 발급·폐기와 Admin 로그인 중계만 맡는다. 클라이언트와 역할 데이터의 관리는 관리 API 서비스가 담당하고, 인증서버는 이를 조회해 사용한다.

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| AS-01 | `JWT` 방식 클라이언트에 `client_credentials` 그랜트로 JWT 액세스 토큰을 발급한다 | Must |
| AS-02 | 토큰 발급 시 클라이언트의 Secret을 HMAC 다이제스트로 검증한다 | Must |
| AS-03 | 액세스 토큰 TTL은 기본값을 두고 클라이언트별로 설정할 수 있다 (기본값·상한 모두 24시간) | Must |
| AS-04 | 토큰 폐기 요청 시 토큰 ID를 Redis 폐기 목록에 등록하고, 해당 토큰의 만료 시각까지 유지한다 | Must |
| AS-05 | JWKS 엔드포인트를 공개하고 서명 키 로테이션을 지원한다 | Must |
| AS-06 | Admin BFF에 대해 OIDC Provider로 동작하고, Google을 상위 IdP로 연동한다 | Must |
| AS-07 | Google ID 토큰의 `hd`(회사 도메인)와 `email_verified`를 검증한다 | Must |
| AS-08 | 로그인 시 이메일–역할 매핑으로 Admin 역할을 부여하고, 초기 관리자는 설정으로 부트스트랩한다 | Must |

## 6. 기능 요구사항: Admin Tool·관리 API 서비스

운영자는 Google SSO로 Admin Tool에 로그인해 클라이언트, 라우트, 역할을 관리한다. 변경은 관리 API 서비스가 MySQL에 저장하고 감사 로그를 남긴 뒤 Kafka 이벤트로 발행하며, 민감한 변경은 관리자 승인 후에만 반영된다.

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| AD-01 | Google SSO로 로그인한다 (인증서버 중계). BFF가 HttpOnly·SameSite 세션 쿠키를 쓰고, 브라우저에는 토큰을 두지 않는다 | Must |
| AD-02 | 역할에 따라 화면과 기능을 제어한다 (관리자 외 역할 세트는 열린 항목) | Must |
| AD-03 | 클라이언트를 등록한다: 이름, 소유 팀, 인증 방식(필수 선택), 허용 IP CIDR(선택), 토큰 TTL(JWT 방식, 24시간 이하, 미입력 시 24시간) | Must |
| AD-04 | Secret을 발급, 재발급, 폐기한다. 서버가 생성해 발급 직후 1회만 표시하고 HMAC 다이제스트로만 저장한다 | Must |
| AD-05 | 클라이언트당 복수 Secret을 동시에 활성화해 무중단 로테이션을 지원한다 | Should |
| AD-06 | 라우트를 관리한다: 경로, 대상 서비스, 허용 클라이언트 | Must |
| AD-07 | Admin 사용자의 이메일–역할 매핑을 관리한다 | Must |
| AD-08 | 민감한 변경(IP, 인증 방식, 권한)은 관리자 승인 후에만 반영한다 | Must |
| AD-09 | 모든 설정 변경을 감사 로그로 기록하고 조회한다: 누가, 언제, 무엇을, 변경 전후 값, 승인자 | Must |
| AD-10 | 반영이 확정된 변경만 Kafka 이벤트로 발행한다 | Must |
| AD-11 | 레거시 클라이언트의 전환 현황(호출량, 종료 예정일)을 보여준다 | Should |
| AD-12 | 클라이언트별 호출 API와 성공·실패율을 조회한다 (Admin Tool 화면에서 제공) | Must |

## 7. 비기능 요구사항

피크 20,000 TPS와 인증서버 장애 시 동작은 확정됐다. Redis 장애 시 동작도 확정됐고, Gateway 지연 목표와 가용성 목표가 남은 핵심 미정 항목이다.

| ID | 분류 | 요구사항 | 목표치·상태 |
| --- | --- | --- | --- |
| NFR-01 | 성능 | 전체 피크 처리량 | 20,000 TPS |
| NFR-02 | 성능 | Gateway가 추가하는 지연 | p99 목표 미정 |
| NFR-03 | 성능 | JWT 요청마다 하는 Redis 폐기 목록 조회가 지연 예산 안에 들어올 것 | 조회 방식 미정 |
| NFR-04 | 성능 | 설정 변경이 Kafka를 거쳐 모든 Gateway 인스턴스에 반영되는 시간 | 미정 |
| NFR-05 | 가용성 | Gateway·인증서버·관리 API 다중 인스턴스, 단일 장애점 없음 | 가용성 목표 미정 |
| NFR-06 | 가용성 | 인증서버 장애 시 신규 토큰 발급은 불가하고, 만료 전 토큰은 계속 사용 가능 | 확정 |
| NFR-07 | 가용성 | Redis 장애 시 폐기 목록 확인은 일시 중단하고 rate limit은 적용하지 않음 (fail-open) | 확정 |
| NFR-08 | 가용성 | Kafka 장애 시 Gateway는 마지막으로 받은 설정으로 계속 동작 | 제안 |
| NFR-09 | 보안 | Secret은 상수 시간 비교, 평문 미저장, 로그·화면 마스킹 | 확정 |
| NFR-10 | 보안 | 실제 클라이언트 IP는 신뢰 프록시 체인 기준으로 판단 | 확정 |
| NFR-11 | 보안 | Gateway(WebFlux) 요청 경로에 블로킹 I/O 금지 | 확정 |
| NFR-12 | 감사 | 인증 실패 로그와 설정 변경 이력 보존 | 1개월 (PCI-DSS 범위면 12개월 필요) |
| NFR-13 | 관측 | 지표는 클라이언트 × 라우트 템플릿 기준으로 집계하고, 원본 경로는 라벨로 쓰지 않음 | 제안 |
